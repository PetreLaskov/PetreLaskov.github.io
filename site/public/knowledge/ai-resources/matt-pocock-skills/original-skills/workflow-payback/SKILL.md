# Workflow Payback

Use when a recurring task looks automatable but its value is unclear. Start from a recent actual run, not an idealized process. Identify frequency, active effort, variability, error consequences, and the part the user wants to keep doing personally. Use ranges when measurements are uncertain.

Compare the smallest credible alternatives: improve the manual process, add a deterministic aid, or build a richer automation. Include setup, maintenance, exception review, and recovery effort. Include meaningful reliability or accessibility benefits that time alone would miss. Do not convert every valued human activity into a cost to eliminate.

Find the uncertainty that could reverse the choice. It might be exception frequency, source consistency, available access, or the time saved per run. Propose the cheapest observation or prototype that resolves it. Prefer examining a few real cases over inventing precise return-on-investment numbers.

Define a pilot with a bounded duration or number of runs, a success measure, and a stop condition. State what will be measured against the present workflow and what counts as an unacceptable burden. Keep the pilot within the user's authorized resources and actions.

Recommend build, simplify, observe, or decline, with one clear reason. If proceeding, hand the chosen workflow to specification or implementation with the payback assumptions attached. After the pilot, compare actual net effort and failures with the prediction. Retire or narrow an automation that does not earn its ongoing cost; do not defend it merely because setup effort has already been spent.
